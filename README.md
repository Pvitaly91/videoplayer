# VideoPlayer — native C++ portable відеоплеєр

Це незалежна паралельна реалізація VideoPlayer на C++17. Вона використовує
Win32 API та LibVLC C API, збирається у Visual Studio 2022 і не містить коду
WPF/.NET-версії.

Програма має звичайне Windows-вікно з власним дочірнім `HWND` для відео,
єдиною панеллю керування, перемотуванням, гучністю, mute, асинхронними
прев’ю на шкалі, зумом вибраної області та borderless fullscreen. LibVLC
завантажується динамічно лише з папки поруч із програмою — встановлений VLC,
`PATH` і реєстр не використовуються.

Іконка Play у помаранчевій рамці зуму вбудована в EXE та використовується
головним вікном і діалогом експорту. Вона містить дев'ять розмірів
від 16 до 256 px; окремий ICO не потрібен під час запуску. Затверджений
PNG, ICO та оригінальний imagegen prompt збережені в
[assets](src/VideoPlayer/assets/README.md). Для відтворення ICO використовуйте
`scripts/convert-app-icon.ps1` (це лише developer tool, не runtime-залежність).

## Приватність і відсутність історії

**VideoPlayer не зберігає список відкритих файлів, позиції перегляду, прев’ю
кадрів або інші дані історії.** Поточний шлях, стан відтворення та обмежений
кеш прев’ю існують лише в оперативній пам’яті. Кеш очищається при відкритті
іншого файла й під час закриття програми; кадри або thumbnails ніколи не
записуються на диск.

Програма не створює MRU, власний Jump List, конфігурацію, базу даних, журнали,
телеметрію або файли в AppData/LocalAppData/ProgramData/Documents чи каталозі
програми. Діалог відкриття використовує `OFN_DONTADDTORECENT`, тому
VideoPlayer не додає вибраний файл до Windows Recent Items. Глобальна історія
Windows та дані інших програм не змінюються.

Коли одночасно відкривається кілька відео, шляхи наступних файлів передаються
новим процесам через анонімну спільну пам’ять і не додаються до їхнього
командного рядка.

Основний і preview LibVLC instance запускаються щонайменше з
`--ignore-config`, `--no-media-library` та `--no-video-title-show`; preview
додатково працює без звуку. Готовий `plugins/plugins.dat` є кешем модулів
пакетного LibVLC, а не історією переглядів.

## Portable-запуск

Готові пакети мають дві архітектури:

- `VideoPlayer-win32-portable.zip` — x86/Win32;
- `VideoPlayer-x64-portable.zip` — x64.

Повністю розпакуйте потрібний ZIP і запустіть `VideoPlayer.exe`. Зберігайте
всю папку разом: `VideoPlayer.exe`, `libvlc.dll`, `libvlccore.dll`, інші
DLL, `plugins` та runtime-каталоги. Перенесення лише
`VideoPlayer.exe` не підтримується.

Для запуску не потрібні:

- .NET;
- Qt;
- встановлений VLC або FFmpeg;
- кодек-паки;
- Visual C++ Redistributable;
- інсталятор чи права адміністратора.

Release збирається зі статичним MSVC runtime (`/MT`), Debug — з `/MTd`.
VLC не запускається як зовнішній процес.

## Відкриття відео

Один або кілька файлів можна відкрити:

1. кнопкою «Відкрити» з одиночним або множинним вибором;
2. перетягуванням одного чи кількох файлів у вікно;
3. передаванням одного або кількох повних шляхів:

   ```text
   VideoPlayer.exe "D:\Відео\перший.mkv" "D:\Відео\другий.mp4"
   ```

Перший файл відкривається в поточному вікні, а кожен наступний — у новому
незалежному процесі VideoPlayer. Тому до восьми відео, вибраних за один раз,
можуть відтворюватися одночасно без спільної позиції, стану чи списку
відтворення. Службова спільна пам’ять передає шлях без дискових файлів.

Діалог показує MP4, AVI, MKV, MOV, M4V, WEBM, WMV, MPG, MPEG, TS, M2TS,
MTS, FLV, 3GP, OGV і VOB, а також усі файли. Розширення не є жорстким
обмеженням: фактичну підтримку контейнера та кодека визначають модулі LibVLC.
Unicode-шляхи, пробіли, абсолютні та UNC-шляхи передаються без тимчасового
копіювання файла. Для extended-length шляхів програма відкриває файл через
Unicode Win32 API та надає LibVLC потокові read/seek callbacks, тому не
залежить від обмеження `MAX_PATH` у файловому шарі LibVLC 3.

## Керування

| Клавіша | Дія |
| --- | --- |
| `Ctrl+O` | відкрити файл |
| `Space` | відтворити / пауза |
| `Left`, `Right` | у зумі — рух області ліворуч / праворуч; без зуму — перемотування на 5 секунд |
| `Ctrl+Left`, `Ctrl+Right` | назад / вперед на 30 секунд |
| `Up`, `Down` | у зумі — рух області вгору / вниз; без зуму — гучність +5 / −5 |
| `M` | звук / без звуку |
| `Ctrl+H` | сховати або відновити панель керування |
| `F`, `F11` | увімкнути або вимкнути fullscreen |
| `Z` | почати вибір області для зуму |
| `Escape` | скасувати вибір, скинути зум або вийти з fullscreen |

Ті самі основні дії доступні стандартними кнопками та повзунками внизу
вікна, включно з кнопкою «Зум області».

### Прев’ю на шкалі

Під час наведення або перетягування повзунка перемотування одразу показується
точний цільовий час біля шкали. Прев’ю використовує більші часові інтервали:
не дрібніше 5 секунд і не більше 120 інтервалів на все відео, включно з довгими
фільмами. Для 40-хвилинного відео крок становить 20 секунд, для двогодинного —
60 секунд. Це не змінює точності самої перемотки.
Біля цільового часу вказується приблизний час кадру, якщо вони різняться.
Кешований кадр показується одразу, без проміжного «Очікування кадру».
Якщо новий кадр ще готується, залишається найближчий кешований або попередній
кадр цього файла з його справжнім часом і позначкою «Оновлюється…». Він не
видається за готове прев’ю нової позиції. Чорне очікування потрібне лише тоді,
коли ще немає жодного придатного кадру.
Після завершеної невдалої спроби показується «Кадр недоступний», а не
нескінченний напис очікування; наступне наведення може повторити запит.

Після відкриття файла, щойно відомі тривалість і можливість перемотування,
один фоновий worker починає підготовку прев’ю без наведення миші. Спочатку
готує початок, кінець і середину, потім заповнює проміжки: вся шкала поступово
отримує до 121 кадру. Робота стартує з невеликою затримкою 400 мс; повний кеш
не готовий миттєво й залежить від швидкості декодування конкретного файла.
Кадри зберігаються лише до зміни відео або закриття програми, без дискового кешу.

Некешований кадр декодує окремий preview-player у тому самому worker
thread зі зниженим пріоритетом; основний player для цього не перемотується.
Запит під курсором перериває фонову підготовку й виконується першим.
Новий інтервал наведення чекає
100 мс стабілізації наведення: швидкий рух об’єднує запити до найновішого,
а сусідні позиції одного інтервалу не скасовують і не затримують декодування.
Для запитів наведення між початками декодування лишається щонайменше 120 мс.
Кеш містить не більше
128 незмінних кадрів лише в RAM (до приблизно 28 МіБ пікселів), а максимальний
кадр має 320×180 logical pixels
з DPI-масштабуванням popup. Виведення виконується GDI з 32-bit RV32 buffer без
GDI+, PNG/JPEG snapshot і тимчасових файлів. Якщо кадр недоступний, timestamp
залишається видимим із placeholder.

Після готового некешованого прев’ю той самий worker заздалегідь готує до
двох сусідніх інтервалів (наступний і попередній). Це обмежена фонова робота
без повторів і без нових потоків. Після цього продовжується загальний план
підготовки; приховування popup його не скидає. Між фоновими кадрами є пауза
щонайменше 120 мс. Невдала фонова спроба пропускає кадр, а помилка runtime
або відсутність відео припиняє план, не забороняючи наступні явні запити.
Підготовлені кадри залишаються в тому самому RAM-кеші та можуть оновити
приблизний кадр у видимому popup, але не змінюють основний playback.

Тимчасовий timeout чи невдалий seek не блокують прев’ю для всього файла:
worker виконує обмежені повтори з backoff, а нове наведення дозволяє нову
спробу, зокрема на тому самому timestamp. Скасування інвалідує лише запит;
зум не змінює generation файла й не очищає справний RAM-cache. Новий
некешований інтервал до отримання відповідного кадру зберігає явно позначений
приблизний кадр, якщо він уже є, або показує placeholder.
Заміна файла швидко інвалідує запити; звільнення старого preview backend виконує worker,
без очікування його cleanup в UI. Стан завершеного через exception worker
явно відмічається, щоб запити не потрапляли у мертву чергу.

На один явний запит дозволено щонайбільше дві спроби, до 3 секунд
очікування кадру кожна, з 80-мс backoff. Це межа очікування кадру, а не
гарантія тривалості LibVLC stop/release. Для некешованого timestamp worker
створює новий preview-player/input з `start-time`, звільнивши попередній
player і його video output. Кожен player має окремий callback-контекст, який
живе до синхронного завершення release; пізній callback старого player не може
заповнити новий запит. LibVLC може спочатку показати спільний preroll-buffer,
тому перший token-matched display buffer не публікується: потрібен наступний
display callback, інакше лишається placeholder. Окремий `get_time` не
використовується як доказ часу показаних пікселів, бо clock може відставати від
display callback. LibVLC instance, один worker і RAM-cache залишаються;
основний player, його звук і crop не змінюються.

### Повтор відео та фрагмента A–B

Кнопка-прапорець «Повтор відео» або клавіша `L` вмикає/вимикає
повтор усього поточного файла. Натиснута кнопка означає активний повтор.

Щоб зациклити фрагмент:

1. Перейдіть на потрібний початок і натисніть «Початок A» або `[`.
2. Перейдіть на потрібний кінець і натисніть «Кінець B» або `]`.
3. Повтор A–B вмикається автоматично. Якщо відео на паузі, натисніть Play.

Межі показані поруч із кнопками з точністю до мілісекунд і підсвічені на
шкалі часу. B має бути щонайменше на 0,5 секунди пізніше A; до цього кнопка
кінця недоступна. Нове A очищає старе B і вимикає повтор, щоб можна було
вільно вибрати новий кінець. «Повтор A–B» вимикає або знову вмикає готовий
фрагмент, а «Скинути A–B» очищає його межі. Повтор усього відео й A–B
взаємовиключні.

При активному A–B відтворення поза фрагментом повертається до A; на паузі
можна перемотувати без автоматичного повернення. Pause/Stop не запускають
відео самостійно. Зум, fullscreen і приховування тулбару зберігають повтор.
Новий файл очищає режим і межі; вони незалежні в кожному інстансі й
зберігаються лише в RAM.

Це звичайний повтор через LibVLC seek/restart, не покадрово точний або
безшовний монтажний цикл: межа перевіряється кожні 100 мс, а фактичний
перехід залежить від декодера. Якщо backend не підтверджує перехід за
5 секунд, повтор вимикається без нескінченних команд.

### Панель і compact mode

У звичайному вікні панель керування початково видима. Кнопка
«Сховати панель керування» або
`Ctrl+H` вмикає ручний compact mode як у звичайному вікні, так і у fullscreen.
У windowed mode панель перестає займати 120 logical pixels, тому відео
розширюється до всієї client area. Ручний стан зберігається через Pause/Play,
resize, minimize/restore, зміну файла, зум і F/F11, але не записується на диск.

Під час ручного приховування наведення у нижні 48 logical pixels фактичної
області відео показує по центру невелику напівпрозору кнопку зі стрілкою вгору.
Клік по ній або `Ctrl+H` відновлює повну панель. Кнопка має alpha 176/255,
не активує вікно, не входить в Alt+Tab і не є global topmost; у Windows High
Contrast вона стає непрозорою. Поза нижньою зоною кнопка ховається.

Без ручного compact mode fullscreen працює як раніше: відео займає всю client
area, а панель з alpha 160/255 накладається знизу. Лише під час Playing вона
автоматично ховається приблизно через 1200 мс бездіяльності. Рух у нижній
activation zone висотою близько 100 logical pixels повертає всю панель. На
паузі, під час відкриття, помилки, завершення чи взаємодії з seek, volume,
preview або focus вона лишається видимою. Під час вибору області зуму панель
та restore-кнопка приховані до завершення або скасування вибору. Один 100-мс
timer працює лише у fullscreen або ручному compact mode; global hook і
окремий thread не використовуються.

Коли панель прихована у fullscreen або ручному compact mode й тривалість
відео відома, по самому нижньому краю показується червона смуга прогресу
заввишки 3 logical pixels. Її ширина відповідає поточній позиції; вона не
приймає фокус і не перехоплює мишу. Після відновлення панелі смуга зникає.

Смуга є окремим owned non-activating popup поверх video output LibVLC,
без global topmost і без залежності від зуму. Slider, час і смуга беруть
узгоджений snapshot основного плеєра кожні 100 мс та після seek/restore.
Мінімізація, деактивація й модальний діалог ховають overlay popups,
скасовують незавершений drag/selection та preview. Втрата capture не
підтверджує seek. Restore узгоджує parent, enabled state і layout; застосований
crop зберігається, а preview з’являється лише після нового наведення.

### Зум області

Наведіть мишу на край або кут самого зображення: курсор зміниться на стрілки
розміру. Затисніть ліву кнопку й тягніть назовні або всередину. Лівий/правий
край змінює тільки ширину області, верхній/нижній — тільки висоту, а кут —
обидві величини незалежно. Пропорції області не заблоковані; зум вмикається
автоматично. Зміна розміру відбувається від центру області.
Це працює і для повного кадру, і для вже вибраної зум-області, у звичайному
вікні та fullscreen. Чорні поля можна заповнити до меж відеообласті.
Змінюється прямокутник source crop, а не пропорції пікселів: зображення
всередині не спотворюється. За наявності запасу розширення відкриває більше
кадру; на межі джерела масштаб рівномірно підлаштовується під нову рамку.

Краї змінюють форму й розмір області в межах viewport, а колесо в зумі
змінює масштаб вмісту зі збереженням останніх заданих пропорцій області.
Перетягування всередині
картинки та стрілки дозволяють оглянути частини кадру, що вийшли за межі
вікна. Повторне натискання Z або Escape скидає обидва види масштабу.
Розмір відображення зберігається відносно viewport при F11, зміні розміру
вікна та приховуванні тулбару. Положення обмежується краями джерела.
Тулбар і кнопка його відновлення зберігають свій ввід поверх відео.

Кнопка «Зум області» або `Z` вмикає неактивуючий selection overlay над
відео. Прямокутник можна тягнути в будь-якому напрямку; мінімальна область —
приблизно 24–32 logical pixels. Координати перетворюються в decoded source
coordinates з урахуванням letterbox/pillarbox, тому чорні поля не входять у
crop. Валідний crop застосовується через LibVLC без спотворення пропорцій.
Зум і fullscreen незалежні: вибір у звичайному вікні залишає його розмір і
положення незмінними; viewport не включає docked toolbar. Preview завжди
показує повний оригінальний кадр.

Після застосування зуму стрілки переміщують область перегляду приблизно на
5% її ширини/висоти за натискання; утримання клавіші продовжує рух.
Затисніть ліву кнопку на зображенні й перетягуйте його, щоб оглянути іншу
частину кадру. Колесо вгору наближає, вниз віддаляє, з кроком приблизно 12%;
точка кадру під курсором зберігає своє положення, доки область не впирається
в межу джерела. Чорні поля й controls не є областю навігації. Навіть коли
фокус на seek/volume, колесо над відео керує зумом, а не перемотуванням.

Область завжди обмежена розміром оригінального кадру. Наближення зупиняється
на меншій стороні близько 16 source pixels, зберігаючи пропорції з точністю
до округлення; для вже меншої початкової області її розмір не збільшується.
Віддалення працює одразу після виділення й розширює область до найбільшого
прямокутника останніх заданих пропорцій, що вміщується в оригінальний кадр.
Пропорції зберігаються з точністю до округлення пікселів. На межі колесо
не скидає режим зуму: можна одразу наблизити знову. Якщо пропорції вибору
збігаються з кадром, максимальне віддалення повертає весь кадр у рамку.
Якщо рамку перед цим розтягнули понад viewport, її надлишок лишається
обрізаним; зменшення краєм або явний reset повертає звичайне відображення.
Явний reset скидає вибір і повертає повний кадр. `Ctrl+Left/Right` продовжують перемотувати
на 30 секунд. `Z` або `Escape` скидають зум і повертають звичайні дії стрілок.
Drag припиняється при втраті capture, resize, переміщенні/згортанні вікна,
F11, зміні файла та reset. Уже обрану область він не скидає.

У fullscreen після натискання кнопки або `Z` нижня панель ховається до
завершення вибору. Overlay охоплює весь видимий кадр, включно з нижньою
частиною, яку перед цим перекривала панель. Після застосування або скасування
зуму панель повертається до звичайного режиму автоприховування.

`Escape` виконує рівно одну дію: Selecting → скасувати selection; Applied →
скинути crop, зберігши режим вікна; None + fullscreen → вийти з fullscreen;
None + windowed → нічого не закривати. `Z` також починає або скидає зум.
Crop зберігається в source coordinates при resize, minimize/restore, seek,
Pause/Play і F/F11 в обидва боки. Новий файл, критична помилка, явний reset та
закриття скидають crop. Кожен процес має незалежні crop, preview й overlay.

## Експорт відео

### Видалити кілька відрізків без перекодування

Позначте «Початок A» і «Кінець B» та натисніть **«Додати A–B до списку»**.
Відрізок зберігається, а поточні A/B і повтор очищаються для вибору наступного.
Збережені відрізки позначені помаранчевим на шкалі прогресу, зокрема на тонкій
нижній смузі при прихованій панелі. Нові A/B не можна ставити всередині них,
а новий інтервал не може перетинати або охоплювати збережений. Відповідні
кнопки блокуються; ця ж перевірка діє для гарячих клавіш. Спільна межа
суміжних відрізків дозволена. Позначення показують вибрані часові межі,
а округлення до ключових кадрів показується окремо перед видаленням.
Повторіть для всіх потрібних відрізків, потім натисніть
**«Видалити відрізки…»**. Одиночний поточний A–B також можна передати
безпосередньо цією кнопкою.

У діалозі можна прибрати вибраний відрізок або очистити список, зберегти
результат у новий файл або перезаписати відкритий оригінал. Усі часи
належать вихідному відео. Перед підтвердженням показуються задані й
**фактичні** інтервали: A округлюється назад, а B — вперед до ключових кадрів.
Інтервали, що перекриваються або дотикаються після округлення, об'єднуються.
Якщо вони видалили б усе відео, збереження блокується.

Усі збережені частини копіюються командою stream-copy та склеюються без
перекодування. Після перевірки контейнера, тривалості, потоків і повного
декодування результат атомарно зберігається. При перезаписі відкритого файла
плеєр звільняє його, підміняє лише після перевірки та відкриває знову.
За помилки або скасування оригінал не змінюється. Додаткові відеопотоки,
субтитри та глави не переносяться; це показано в діалозі.
Список існує лише в пам'яті поточного вікна. Збереження нового файла чи
скасування лишає його для подальшого редагування; відкриття іншого відео
або успішний перезапис оригінала очищає список.

Кнопка **«Зберегти відео…»** або `Ctrl+E` відкриває український modal dialog.
Exporter працює з даними вихідного файла через bundled `ffprobe.exe` і
`ffmpeg.exe`; це не запис екрана і не залежність від установленого FFmpeg чи
`PATH`. Аналіз запускається лише при відкритті exporter, тому звичайне
відкриття/відтворення лишається на LibVLC.

Можна зберегти повне відео або готовий фрагмент A–B незалежно від того, чи
увімкнений його повтор, повний кадр або фактично видиму частину поточного
зуму, вихідний canvas або нативний розмір crop, оригінальне аудіо або файл
без аудіо. За замовчуванням пропонуються A–B (якщо межі валідні), застосований
зум, **фізичний native crop**, аудіо та точний метод. Для native crop
розмір encoded frame дорівнює видимій області, а target video bitrate
пропорційно зменшується за площею кадру. Тому вибрана зум-область
не доповнюється чорними полями. Опційний режим полотна джерела
лишається доступним і явно позначений як такий, що може додати black padding.
Повний кадр — як усе відео, так і A–B — копіюється без перекодування відео
й аудіо. Для A–B аналізуються ключові кадри: A округлюється назад, B вперед;
запитані та фактичні межі показані до підтвердження. Якість і кодеки джерела
зберігаються; відсутність енкодера не заважає копіюванню. Несумісний контейнер
потребує вибору сумісного (наприклад MKV), без прихованого transcode.
Перекодування потрібне лише для експорту зміненої картинки зуму. Фрагмент,
який не пройшов повне декодування (наприклад відкритий GOP), не зберігається;
автоматичного перекодування замість копіювання немає.

Якщо джерело не має аудіо, «Зберегти аудіо» не заважає збереженню відео.
Порожня аудіодоріжка або A–B після завершення звуку також допускають результат
без аудіо: перед прийняттям exporter перевіряє фактичні звукові дані джерела
в цьому інтервалі. Втрата наявного звуку чи невдала перевірка лишаються помилкою.

Перед запуском dialog показує container, main video codec/profile,
роздільність, SAR, rational fps, pixel format/bit depth, rotation, audio,
кількість потоків/розділів і фактичний план. Main video map задається явно;
cover art, додаткове video, subtitles, attachments і chapters не копіюються,
про що summary повідомляє до запуску. Crop обчислюється чистою функцією з
source crop, presentation rect і його перетину з viewport: чорні поля й
overlay toolbar не входять, а clipping/pan/scale, SAR і metadata rotation
враховуються без подвійного autorotate.

Перед відкриттям діалогу фіксуються path/file identity, generation, A–B,
crop, render/presentation і viewport. Після підтвердження job плеєр знову
доступний: відтворення й preview продовжуються, можна відкрити інший файл,
а вже запущений export не змінює свій snapshot. Дозволений один активний
export job на процес. Закриття плеєра під час job окремо пропонує скасувати
експорт; cleanup завершується перед закриттям.

Робота виконується у background thread. FFmpeg запускається абсолютним
Unicode шляхом через `CreateProcessW` без console/shell, stdout і stderr
дренуються окремо, `-progress pipe:1` оновлює progress, а Cancel спочатку
надсилає `q` лише приватному stdin і потім завершує лише власний Job Object.
Результат спочатку пишеться як `<ім’я>.<job-id>.part` у цільовому каталозі.
Після ffprobe-перевірки container/duration/streams/dimensions/audio і повного
decode-check файл атомарно перейменовується; source identity звіряється зі
snapshot до запуску й перед фіналізацією, а destination identity, hard links,
race та перезапис перевіряються окремо. Partial після помилки або
скасування видаляється. Історія export paths не зберігається.

Підтримані вихідні контейнери: MP4, Matroska і WebM. При transcode planner
обирає software encoder тієї самої codec family (H.264/HEVC/MPEG-4/VP9/AV1),
не додає штучний `-r 30` і явно переносить pixel/color parameters. Невідомий
codec може перейти на H.264/AAC MP4 лише після окремого підтвердження;
HDR/10-bit не знижується до SDR/8-bit непомітно.

## Збірка

Потрібні Visual Studio 2022 (workload **Desktop development with C++**),
Platform Toolset v143 і Windows SDK. NuGet, vcpkg, Conan і CMake не потрібні.

### Відновлення з GitHub на чистому комп’ютері

Поточна native C++ версія зберігається в гілці `codex/native-cpp-portable`.
Встановіть Git та зазначені вище компоненти Visual Studio, відкрийте PowerShell:

```powershell
git clone --branch codex/native-cpp-portable --single-branch https://github.com/Pvitaly91/videoplayer.git
cd videoplayer
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/build.ps1 -Platform x64 -Configuration Release
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/package.ps1 -Platform x64
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/verify-package.ps1 -Platform x64
```

Готова програма буде в `artifacts/VideoPlayer-x64-portable`, архів — поруч.
Для 32-бітної версії замініть `x64` на `Win32` у трьох командах.
Перший запуск збірки потребує інтернету: скрипти самі завантажують LibVLC та
FFmpeg, перевіряють SHA-256 і готують потрібні бібліотеки. Вихідні файли,
тести, ресурси іконки та скрипти містяться в Git; ключ до генератора зображень
для збірки не потрібен.

Каталоги `build`, `third_party` та `artifacts` і проміжні файли компіляції
не є вихідними даними: вони створюються повторно цими командами. Для запуску
плеєра копіюйте всю portable-папку з DLL, `plugins` та `tools`.

Скрипт завантаження бере офіційні архіви VLC/LibVLC 3.0.23 з
`download.videolan.org`, завантажує офіційний файл SHA-256, перевіряє
контрольну суму, розпаковує runtime окремо для Win32 і x64 та один раз створює
`plugins/plugins.dat` офіційною утилітою `vlc-cache-gen.exe`. До portable-
пакета потрапляє готовий кеш, але не утиліта його генерації:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/fetch-libvlc.ps1 -Platform Win32
powershell -ExecutionPolicy Bypass -File scripts/fetch-libvlc.ps1 -Platform x64
powershell -ExecutionPolicy Bypass -File scripts/fetch-ffmpeg.ps1 -Platform Win32
powershell -ExecutionPolicy Bypass -File scripts/fetch-ffmpeg.ps1 -Platform x64
```

Архіви та runtime зберігаються у
`third_party/libvlc/3.0.23/{win32,win64}` і `third_party/ffmpeg/` та не
комітяться. Після першого
завантаження post-build крок Visual Studio інкрементально додає runtime до
папки результату, тому F5 не потребує ручного копіювання сотень мегабайт.

Команди окремих збірок:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build.ps1 -Platform Win32 -Configuration Debug
powershell -ExecutionPolicy Bypass -File scripts/build.ps1 -Platform Win32 -Configuration Release
powershell -ExecutionPolicy Bypass -File scripts/build.ps1 -Platform x64 -Configuration Debug
powershell -ExecutionPolicy Bypass -File scripts/build.ps1 -Platform x64 -Configuration Release
```

`build.ps1` знаходить Visual Studio через `vswhere`, викликає MSBuild,
збирає обидва native-проєкти та запускає `VideoPlayer.Tests.exe`.
Конфігурації solution: Debug/Release × Win32/x64.

## Пакування та перевірка

Після відповідної Release-збірки можна створити один пакет:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/package.ps1 -Platform Win32
powershell -ExecutionPolicy Bypass -File scripts/package.ps1 -Platform x64
```

Повний локальний цикл очищає `artifacts`, збирає чотири конфігурації,
запускає native-тести, створює обидва пакети, запускає headless self-test і
перевіряє вміст та залежності:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build-all.ps1
```

Результати:

```text
artifacts/VideoPlayer-win32-portable/
artifacts/VideoPlayer-win32-portable.zip
artifacts/VideoPlayer-x64-portable/
artifacts/VideoPlayer-x64-portable.zip
```

Окрему перевірку можна повторити командами:

```powershell
powershell -ExecutionPolicy Bypass -File scripts/verify-package.ps1 -Platform Win32
powershell -ExecutionPolicy Bypass -File scripts/verify-package.ps1 -Platform x64
```

Перевірка контролює PE-архітектуру EXE та всіх DLL, наявність непорожніх
`plugins` і `plugins/plugins.dat`, заборонені SDK/PDB/.NET-файли, результат
`VideoPlayer.exe --self-test`, ZIP та `dumpbin /dependents`. Вона також
перевіряє production source на API/рядки runtime persistence, а portable-
папку й ZIP — на log/tmp/history/recent/settings та дискові preview-кеші.
Імпорти `MSVCP140.dll` або `VCRUNTIME140.dll` вважаються помилкою.

GitHub Actions запускає той самий `build-all.ps1` на
`windows-2022` для push у `codex/native-cpp-portable` або вручну та
публікує два artifacts: `VideoPlayer-win32-portable` і
`VideoPlayer-x64-portable`.

## Сумісність Windows

Проєкти задають `WINVER=0x0601`, `_WIN32_WINNT=0x0601` і мінімальну
версію subsystem 6.01. Код не вимагає AVX/AVX2/AVX-512, WinRT, Windows App
SDK або обов’язкових Windows 10/11 API.

Налаштовані compatibility targets:

- Windows 7 SP1;
- Windows 8.1;
- Windows 10;
- Windows 11.

Локально збірки, native tests, `--self-test` і перевірку portable-пакетів
фактично виконано на Microsoft Windows 11 Pro x64, версія 10.0, build 26200.
Windows 7 SP1, Windows 8.1 і Windows 10 залишаються лише налаштованими
compatibility targets: реального запуску на них не виконано.

Регресійні тести викликають production-компоненти з fake backend, ін'єкцією
помилок і прихованими HWND. Окремо виконано інтеграційні запуски справжнього
LibVLC на згенерованих відео з таймкодом. Це не інтерактивна GUI-перевірка.
Desktop automation у цьому середовищі не запустилась через помилку sandbox
helper; фактично виконано **0 інтерактивних GUI-циклів**. Не перевірено
візуальний Z-order смуги над LibVLC без crop, читабельність alpha 160,
живі жести drag/колеса для навігації в зумі,
30 повних GUI-циклів, три видимі процеси поруч, інші монітори та різні DPI.
Приховані controller fixtures і `--self-test` не замінюють цих перевірок.
`--self-test` перевіряє runtime, ABI, версію LibVLC і створення двох MediaPlayer,
але не декодує відео.

Фактичні результати та відомі затримки backend наведені у
[`VALIDATION.md`](VALIDATION.md). Результат CI поточного commit доступний
у GitHub Actions після push.

## Відомі обмеження

- немає плейлиста;
- немає медіатеки;
- немає вибору аудіодоріжки;
- немає ручного підключення субтитрів;
- немає інсталятора;
- немає асоціації файлів;
- preview є best-effort: точність кадру залежить від seek/index конкретного
  контейнера й кодека;
- SAR/rotation export mapping перевірено deterministic geometry tests;
  живий GUI з rotated/non-square-SAR джерелом у цьому середовищі не пройдено;
- зум області доступний лише після того, як активна відеодоріжка віддала
  decoded video size.

Відомості про компоненти VLC/LibVLC та їхні ліцензії наведено у
[`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md).
